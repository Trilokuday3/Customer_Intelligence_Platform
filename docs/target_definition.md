# Target & Time-Window Definition

This is the point-in-time design referenced throughout the codebase
(`src/data/config.py` is the source of truth for the actual date/day
values — if the two disagree, the code is right and this doc is stale).

## Timeline

```
DATA_START (2024-01-01)
   |
   |  historical observation window
   v
OBSERVATION_CUTOFF (2025-12-31)   <- "prediction date": every feature is
   |                                 computed using only data at/before
   |  churn horizon (90 days)        this timestamp
   |  CLV horizon (180 days)
   v
DATA_END (2026-06-30)
```

- **Observation cutoff**: `2025-12-31`. This is the point-in-time snapshot
  date. All churn/CLV features for a customer must be computable using
  only rows with `order_date`, `event_time`, or `created_at` `<= cutoff`.
- **Churn horizon**: 90 days after cutoff (`2026-01-01` to `2026-03-31`).
- **CLV horizon**: 180 days after cutoff (`2026-01-01` to `2026-06-29`).
- **Active-customer lookback**: 180 days before cutoff.

## Churn definition

A customer is **eligible for a churn label** only if they were "active"
as of the cutoff: at least one `completed` order in the 180 days before
cutoff (`ACTIVE_LOOKBACK_DAYS`). This excludes customers who were already
long-dormant or never meaningfully engaged — for them, "will they churn"
is not a well-posed question at this cutoff.

For an active customer, **churn = 1** if they have zero `completed`
orders in the 90-day churn horizon after cutoff, else **churn = 0**.

Rationale for the 180-day active window / 90-day horizon split: most
customers in the synthetic catalog purchase every few weeks to a couple
of months, so a 6-month lookback is long enough to catch normal
purchase-interval customers as "active" without also catching people who
made one purchase two years ago and never returned (those are dormant,
not "at risk"). This mirrors real subscription/e-commerce practice of
defining churn as *no qualifying activity within a defined future
window*, not as a permanent state.

On the current synthetic dataset (`scripts/generate_data.py`, seed 42,
8,000 customers): **5,097 customers (64%) are active at cutoff**, and of
those, **~29% are labeled churned** in the 90-day horizon. That is a
deliberately moderate class imbalance — enough signal for classification
metrics (PR-AUC, precision@K) to be meaningful, not so rare that the
label is unusable.

## CLV definition

**Predicted CLV** = total net revenue (`amount` on `completed` orders,
i.e. excluding `refunded`/`cancelled`) generated by the customer during
the 180-day CLV horizon after cutoff. This is a *revenue*, not margin,
definition — there is no cost-of-goods field in the synthetic catalog,
so margin-based CLV is out of scope unless a margin/cost table is added
later.

**Historical CLV** (for descriptive reporting only, never as a model
feature) = cumulative net revenue from signup through cutoff.

## Leakage rules

These are enforced by the feature-engineering layer (Phase 4), not by
the raw data itself — the raw tables intentionally contain the full
history (including the future window) so different phases can compute
different point-in-time cuts. Rules:

- No feature may use `order_date`, `event_time`, or `created_at` after
  `OBSERVATION_CUTOFF`.
- The churn label itself, and any post-cutoff support ticket, must never
  appear as a feature.
- Cohort/RFM/behavioral features are always computed relative to the
  cutoff, not to "now" or to each row's own last-event date.

## Known messiness (intentional)

- ~2% of orders are `cancelled`, ~4% `refunded` — both excluded from
  "qualifying" activity for churn/CLV purposes but retained in the raw
  table (a real business's order table looks like this).
- Customers who churn (per the internal simulation) get a 60–90 day
  ramp-down in event rate beforehand rather than an abrupt stop, so
  "recency" and "engagement trend" features carry real predictive
  signal instead of the label being trivially recoverable from a single
  cliff-edge cutoff.
